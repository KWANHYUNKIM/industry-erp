## 3. 메뉴(nav) 로 나눌까, 기능으로 나눌까

사용자 제안: 큰 nav(재고 I) → 작은 nav(영업관리 · 구매관리 …) 대로 `pages/` 를 나누기.

| | 메뉴대로 (`pages/inventory1/sales-mgmt/…`) | 기능대로 (`pages/trade/sales/…`) |
|---|---|---|
| 찾기 | 화면에서 본 메뉴 그대로 찾기 쉽다 | 업무 이름으로 찾는다 |
| 백엔드와 짝 | 안 맞는다(백엔드는 기능 패키지) | **`com/erp/trade/sales` ↔ `pages/trade/sales` 1:1** |
| 메뉴 바뀜 | 원본 메뉴가 바뀌면 폴더도 옮겨야 함(10-03 원본 디자인 · 메뉴가 실제로 바뀌었다) | 메뉴만 고치면 됨 |
| 한 화면이 여러 메뉴에 | MyPage 예시 폴더 · 출력물 · 바로가기에 같은 화면이 있다 → 어디 둘지 애매 | 화면은 기능 폴더 하나에만 |

**추천: 기능대로 나누되, 기능 이름은 원본 작은 nav 와 대체로 맞춘다.** 재고 I 영업관리의 견적서 · 주문서 · 판매 · 출하지시서 · 출하는
그대로 기능 폴더가 되므로 결과적으로 작은 nav 와 거의 같아진다. 메뉴만의 묶음(출력물 › 영업관리현황 등)은 폴더가 아니라 `EcountLayout` 메뉴 표에서 묶는다.

## 4. 프론트 목표 구조

```
frontend/src/
├─ app/                      # 라우트 · 레이아웃 · 프로바이더 (지금 그대로)
│  └─ routes/                # router.tsx 1,128줄 → 모듈별 라우트 조각(trade.routes.tsx …)을 모아 붙인다
├─ pages/<모듈>/<기능>/       # URL 하나 = 화면 하나, 기능 폴더 안에
│  └─ trade/
│     ├─ sales/              # 판매조회 · 판매입력 · 판매입력II · 판매현황 · 결제내역 …
│     ├─ purchase/           # 구매조회 · 구매입력 · 구매현황 · 구매단가일괄변경
│     ├─ quotation/  salesorder/  shipmentorder/  shipment/
│     ├─ purchaseorder/  purchaserequest/  purchaseplan/  pricerequest/
│     ├─ price/              # 특별단가 · 단가변동 · 단가일괄
│     ├─ partner/            # 거래처 · 거래처관리대장
│     ├─ arap/               # 채권 · 채무 · 월별채권채무 · 수금 · 지급
│     ├─ report/             # 판매구매집계 · 현황누계 · 피벗 · 미판매/미구매/미주문 현황
│     └─ export/  mall/  salesplan/
├─ features/<기능>/          # 기능 전용 부품 · api · hooks (지금 69개 — 페이지와 이름을 맞춘다)
├─ components/  utils/  styles/  api/  types/   # 공용 (지금 그대로)
```

- `pages/accounting`(180) 도 같은 방식: `journal/ · ledger/ · bank/ · card/ · note(어음)/ · asset/ · vat/ · withholding/ · yearend/ · expense/ · cost/ · report/ …`
  — 백엔드 accounting 기능 패키지(48)와 이름을 맞춘다.
- 큰 파일 쪼개기: `TradeEntry.tsx`(3,256줄)는 판매 · 구매 공용 입력이다. **머리 칸 · 품목 격자 · 아래 줄 · 이익계산 · 불러오기 창**을
  `features/trade-entry/` 의 부품으로 빼고, 판매/구매 차이는 설정 객체로. (한 파일 1,000줄 넘으면 쪼갤 신호로 삼는다.)
- 규칙(린트로 막기): `pages/A/x` 는 `pages/A/y` 를 import 하지 않는다(공유할 것은 `features/` · `components/` 로). `features/` 끼리 직접 import 금지.
  `qa/arch-check.mjs` 에 프론트 규칙을 더하거나 ESLint `import/no-restricted-paths`.
- barrel(index.ts)은 만들지 않는다(Vite 트리셰이킹 · 순환 위험).

# QA 시드 · 시나리오 검증

핵심 업무 흐름이 실제로 동작하는지 API를 끝까지 몰아보며 확인합니다. 의존성 없이 Node 18+ 만 있으면 됩니다.

## 실행

```bash
# 백엔드(8081)와 Postgres가 떠 있어야 합니다
node qa/qa.mjs          # 시드 + 검증 (기본)
node qa/qa.mjs seed     # QA 마스터 데이터만 생성
```

통과하면 exit 0, 하나라도 실패하면 실패 항목을 출력하고 exit 1로 끝납니다. CI에 그대로 물릴 수 있습니다.

환경변수로 대상을 바꿀 수 있습니다: `ERP_API`(기본 `http://localhost:8081/api`), `ERP_USER`, `ERP_PASS`.

## 반복 실행

마스터 데이터(`QA-` 접두사: 창고·거래처·품목·BOM·공정·로트)는 **있으면 재사용**하므로 몇 번을 돌려도 안전합니다.
다만 전표(수주·출하·생산실적·검사)는 실행할 때마다 새로 쌓입니다. 삭제 API가 없는 전표가 있어 스크립트가 지우지 않습니다.

깨끗한 상태에서 다시 시작하려면 DB를 통째로 초기화하세요.

```bash
docker compose down -v && docker compose up -d
# 백엔드 재기동 → Flyway가 V1~V3를 실행해 스키마를 새로 만들고, 기본 시드가 들어갑니다
cd backend && ./mvnw spring-boot:run
```

> ⚠️ `down -v`는 **DB를 완전히 지웁니다.** 남겨야 할 데이터가 있으면 먼저 백업하세요.
> ```bash
> docker exec erp-postgres pg_dump -U erp erp > backup.sql
> ```

## 스키마를 바꿀 때

`ddl-auto: validate` 입니다. **엔티티만 고치면 기동이 실패합니다.** 반드시 마이그레이션을 함께 추가하세요.

1. `backend/src/main/resources/db/migration/V<다음번호>__설명.sql` 추가
2. 백엔드 재기동 → Flyway가 적용
3. `node qa/qa.mjs` 로 회귀 확인

`V1__baseline_schema.sql`은 수정하지 마세요. 이미 적용된 마이그레이션을 고치면 체크섬이 어긋나 기동이 실패합니다.

## 프론트 타입체크

```bash
cd frontend && npm run typecheck     # tsc --noEmit -p tsconfig.app.json
```

> ⚠️ **`npx tsc --noEmit` 만 치면 아무것도 검사하지 않고 통과합니다.**
> 루트 `tsconfig.json` 은 `"files": []` + project references 구조라, 프로젝트를 지정하지 않으면
> 검사 대상이 0개입니다. 반드시 `npm run typecheck`(또는 `npm run build`)로 확인하세요.

## 죽은 화면 찾기 (브라우저)

**타입 검사와 QA 하네스가 다 통과해도 화면이 통째로 안 뜰 수 있습니다.**
실제로 수금현황·지급현황·결제내역자료비교 셋이 그렇게 죽어 있었고, 아무도 몰랐습니다.
`periodOf('이번기수')!` 처럼 **null 을 `!` 로 눌러** 놓으면 타입 검사는 아무 말도 안 하고
화면을 열 때 터집니다. (그 패턴 자체는 `ui-check.mjs` 2-s 가 이제 잡습니다.)

다른 부류까지 훑으려면 브라우저로 라우트를 지나가며 **콘솔 오류**만 봅니다 — 화면마다
스크린샷을 찍을 필요가 없어 빠릅니다.

1. 라우트 목록: `grep -o 'Route path="[^"]*"' frontend/src/App.tsx`
2. 콘솔을 비우고(`clear`) 라우트 7~8개를 이어서 열고, 마지막에 한 번만 오류를 읽습니다.
3. 거를 것: 확장 프로그램 잡음(`Could not establish connection`, `Language detection`).
   **앱 오류만** 보려면 `TypeError|src/pages` 로 거릅니다.
4. 걸리면 그 화면만 다시 열어 스택을 봅니다.

방법이 실제로 무는지 한 번 확인하고 쓰세요 — 고쳤던 버그를 잠깐 되돌려 걸리는지 봅니다.

## 아직 안 맞춘 것 — 목록과 <b>왜 남아 있는지</b>

원본과 대조하다 나온 차이 가운데 한 판에 못 고치는 것은 fixture 에 적어 두고
<b>늘지만 않게</b> 합니다. 목록만 있으면 다음 사람이 같은 것을 다시 파므로,
갈래와 까닭을 여기 적습니다.

| 목록 | 무엇 | 왜 남아 있나 |
|---|---|---|
| `pending-conditions.json` | 원본에 있는데 우리 화면에 없는 <b>조건</b> | 아래 세 갈래 |
| `pending-columns.json` | 원본에 있는데 우리 표에 없는 <b>열</b> | 아래 세 갈래 |
| `ecount-missing-columns.json` | 짝지은 표에 없는 열 | 값 자체가 없는 것들 |

### 갈래 1 — 엔티티에 그 값이 없다 (마이그레이션이 필요하다)

가장 많은 갈래입니다. `PurchaseOrder`·`Quotation`·`QualityInspection`·`StockTransfer`·
`VacationRequest` 에 <b>프로젝트가 없어서</b> 그 화면들의 [프로젝트] 조건을 못 만듭니다.
`CreditCard`·`BankAccount` 에는 코드·검색창내용·외화통장·이체정보 칸이 없습니다.

컬럼을 늘리려면 `db/migration` 과 `db/tenant` <b>양쪽</b>에 넣어야 하므로
(CLAUDE.md 7.4) 혼자 정하지 않고 상의합니다.

### 갈래 2 — 화면 구조가 다르다 (열을 더한다고 좁혀지지 않는다)

- <b>매출계획</b>(31칸): 원본은 일자-No.·거래처명·담당자명·창고명·품목명·금액을 가진
  <b>전표</b>인데 우리는 연월 × 품목의 <b>계획 대 실적 비교표</b>입니다.
- <b>특별단가등록</b>(6칸): 원본은 거래처설정·창고설정·품목설정·품목그룹설정을 가진
  <b>그룹 마스터</b>인데 우리는 품목별 특별단가입니다.

둘 다 자료 모양부터 다릅니다. 어느 쪽으로 갈지 정하는 것이 먼저입니다.

### 갈래 3 — 원본에 그 기능이 있고 우리에겐 없다

[그래프로 보기](여덟 화면)·[수취금액]·[이력]·[상세내역] 같은 것들입니다.
만들 수 있지만 화면 하나짜리 일이 아니라 기능 하나를 만드는 일입니다.

가장 큰 것은 <b>품목등록의 여섯 탭</b>입니다 — 원본은 등록 폼을 품목정보·수량·단가·
원가·부가정보·관리대상으로 나누는데 우리는 한 화면에 죽 폅니다.
<b>대외 전송</b>(의료기기공급내역보고)도 여기 듭니다 — 심평원 채널·인증서가 없어
산출·보관·이력까지가 범위입니다.

원본 탭 가운데 <b>결재중·미확인·확인</b> 무리는 갈래 3 이 아닙니다 —
우리 전표에 <b>결재·확인 상태 자체가 없어서</b> 탭만 만들면 늘 빈 목록이 됩니다.

### 이미 걷은 것

<b>서버가 이미 보내는데 화면이 안 받던 값</b>은 전부 걷었습니다 — 그게 가장 값이 컸습니다.
프로젝트명·창고명·담당자명이 응답에 오는데 화면 `interface` 가 그 필드를 선언하지 않아
<b>보이지도 거를 수도 없던</b> 자리가 스무 곳 넘게 있었습니다.

### 지도(.ordermap.json)를 더 넓히기 전에 — <b>이름이 닮았다고 같은 화면이 아니다</b>

사본에는 우리 지도에 없는 화면이 아직 백 개 넘게 있고, 이름 줄기로 짝을 지어 보면
그럴듯한 후보가 나온다. 하지만 <b>열을 견줘 보면 다른 화면인 경우가 많다.</b>

| 사본 화면 | 그럴듯한 후보 | 실제로는 |
|---|---|---|
| 비용내역<b>조회</b> | 비용내역현황(ExpenseDetailPage) | 열이 전표번호·사용자·비고·<b>결제구분·출장지</b> — 우리가 만든 [비용내역현황]은 일자-No.·사용자명·사용일자·적요다. <b>다른 화면</b> |
| 시리얼/로트No.<b>내역조회</b> | 시리얼/로트No. 관리(SerialLotPage) | 열이 일자-No.·수량·<b>전표구분·연결전표-No.</b> — 로트 <b>이동 이력</b>이다. 우리 화면은 로트 <b>마스터 목록</b> |
| 생산입고 I·II·III | 이미 지도에 있음 | 사본이 <b>같은 화면을 긴 이름·짧은 이름</b> 둘로 담았다. 둘 다 걸면 같은 빚이 두 번 세어진다 |

그래서 짝을 지을 때는 <b>열 이름을 실제로 견줘 보고</b> 건다. 이름만 닮은 것을 걸면
"안 만든 열" 목록이 <b>만들 필요가 없는 것</b>으로 부풀고, 그 목록을 믿을 수 없게 된다.

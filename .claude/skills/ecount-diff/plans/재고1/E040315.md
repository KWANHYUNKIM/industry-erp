## 2. 우리 흐름(코드로 읽음 — 다시 하기 작업자가 화면으로 다시 확인)

- 발주요청입력 저장 → `POST /purchase-orders` → REQUESTED 한 장(발주계획입력은 `plan: true` → 바로 PLANNED).
- 발주요청조회 [다른전표생성 › 발주계획] → `POST /purchase-orders/{id}/plan` — **같은 전표**가 PLANNED 로 바뀐다. 원본처럼 수량을 고친 새 계획(6)을 따로 만들 수 없고,
  같은 요청을 두 번 넘기면 '이미 발주계획으로 넘어간 발주요청입니다.' 로 막는다(원본은 막지 않고 또 10 을 베낀다).
- 요청의 [종결여부] 는 사람이 정한 값이 없으면 ORDERED · RECEIVED 일 때 '완료' — 원본은 다음 전표가 생겨도 진행중.
- 계획 → 발주서: 원본 [다른전표생성 › 발주서 › 1장라인별 …] 창 대신 우리는 단가확정(prices) → 발주확정(confirm) 상태 이동. 거래처는 줄 거래처 · 첫 줄 거래처.
- 발주서 → 구매: 우리도 구매 줄 `sourceOrderId` 로 잇고 `findUnpurchased` 가 발주수량 − 구매수량으로 미구매를 낸다(원본 잔량적용과 같은 생각). `receive` 는 전량만.
- 삭제: 우리는 구매가 잇힌 발주를 막는다('입고된 구매전표가 있어 지울 수 없습니다…'). 요청 · 계획 · 발주가 한 장이라 요청만 지우는 일이 없다.
- 확인 글: 원본 발주요청 선택삭제 `전표를 삭제하겠습니까?\n- 발주요청조회`, 우리 `전표를 삭제하겠습니까?\n- 발주요청 n건`.

## 3. 다른 점 · 고칠 순서(다시 하기)

1. **결정 필요(스키마)**: 발주요청 · 발주계획을 발주서와 다른 전표(표)로 가를지. 가르면 — `purchase_requests` · `purchase_plans`(머리 + 줄, 줄에 출처 전표 id · No.),
   발주서 줄에 출처 계획 줄, 지금 `purchase_orders.status` 의 REQUESTED · PLANNED · PRICED 자료 옮기기(마이그레이션은 `bash qa/next-migration.sh`, 본사 · 테넌트 둘 다).
   단가요청(E040318~)이 계획 단계의 단가를 받으므로 단가요청 묶음과 같이 정한다.
2. 발주계획입력 [발주요청] 단추 → '발주요청검색창(조회)'(알약 · 열 · 단추 위 1 의 2) → 체크 → 적용(F8) 로 줄을 베낀다. 적용 뒤 [발주요청] · [전표불러오기] 를 숨긴다. 줄 열 [발주요청] · [No].
3. 발주요청조회 [다른전표생성 › 발주계획] 은 상태 이동이 아니라 '발주계획입력' 창을 요청 줄이 찬 채로 띄운다(원본 견적 → 주문서 1장라인별과 같은 틀).
4. 요청 진행상태 '조회' → '발주계획번호확인' 은 이 요청에서 만든 계획 번호들(여럿일 수 있음).
5. 요청의 종결여부는 다음 전표가 생겨도 진행중 — flowProgress 의 'ORDERED → 완료' 를 뺀다.
6. 발주계획조회 [다른전표생성 ▴] 판: '발주서' 줄에 다섯(거래처별납기일자별라인별 · 거래처별납기일자별품목별 · 1장라인별 · 1장품목별 · 직접설정) — 지금 우리 메뉴는 '발주서' 하나.
7. 발주요청 선택삭제 확인 글 `- 발주요청조회`(원본 글자 그대로), 계획이 잇혀도 막지 않는다.
8. 흐름 시험 `qa/flows/` 에 요청 10 → 계획 6 → 발주서 6 → 구매 4 → 미구매 2.00 · 미구매부가세 20 → 지움 을 더한다.

## 4. 못 잰 것

- 계획 → 발주서를 두 번 했을 때 잔량이 줄어드는지, [수량조정] 창 결과, 구매가 잇힌 발주서 삭제가 막히는지.
- 요청 · 계획의 수정 창(저장 뒤 진행상태 변화), 디자인 값(getComputedStyle) — 이번엔 흐름만 쟀다.
- 원본 자료는 모두 지웠다(요청 26/10/20-1 · 계획 2026/10/20 -2 · 발주서 26/10/20-1 · 구매 2026/10/20 -8).

## 규칙

1. **하단 버튼줄은 본문(`.contents`) 바로 다음에 흐른다.** 본문 칸은 위아래 여백 9(격자 위 132 = 틀 123 + 9, 격자 끝 + 9 = 버튼줄 위).
   자료가 창보다 길면 버튼줄이 창 바닥에 붙는다(`footer-fixed` — 스크롤해도 그 자리). 짧으면 격자 바로 아래에 있고 그 아래는 빈 틀이다.
   → 모든 화면이 같다 · **공용으로 고침.**
2. **목록 격자 머리는 700, 입력 격자 머리는 400.** 목록 6개(조회 · 리스트 · 등록 · 현황) 모두 700, 전표 입력 격자(구매입력)만 400.
   → EcListShell 안의 격자를 700 으로 · **공용으로 고침.** (원본이 400 인 출력물 `ec-report-head400` 은 그대로 둠)
3. **조건 판 처음 상태는 머리에 빠른 검색칸 [Search(F3)] 이 있느냐로 갈린다** — 제목 끝말('조회' · '현황')이 아니다.
   - 검색칸이 있는 화면(판매조회 · 사원리스트 …): 조건 판은 **접혀 있다.** 빈 검색칸으로 [Search(F3)] 를 누르면 펼친다.
   - 검색칸이 없는 화면(채권거래내역 · A/S수리현황 같은 현황 · 내역): 조건 판이 **펼쳐져 있고** 격자는 없다. [검색(F8)] 을 누르면 판이 접히고 격자가 나온다.
4. **조건 판 아래 버튼줄은 [검색(F8)│▾] [다시작성]** — 모든 화면 같다. ▾ 는 기간 빠른선택(금일 · 전일 · 금주(~오늘) · 전주 · 금월(~오늘) · 전월 · 종료일 · 최근30일 · 설정 …, 화면마다 몇 개 더 · 덜).
   **[닫기] 는 원본에 없다.** 휴대폰 폭에서는 끝에 ⋯(btn-header-search-btn-more)가 더 붙는다.
   펼쳐서 시작하는 현황(A/S수리현황 E040611, 2026-10-13 2차 실측)은 기간 빠른선택이 ▾ 가 아니라 [검색(F8)] 옆에 **단추로 늘어서고**
   (금일 · 전일 · 금주(~오늘) · 전주 · 금월(~오늘) · 전월 · 직전분기 · 직전반기 · 종료일 · 설정, h21 · btn-sm), 끝에 [다시 작성].
   [검색(F8)] 뒤 판이 접히고 머리에 빠른 검색칸 + [Search(F3)] 가 생기며, 다시 펼친 판도 같은 줄이다.

5. **출력물 격자(머리 6px 3px 3px · 본문 3px, 우리 `.ec-report`)의 선은 1px**, 목록 여백 격자(머리 9px 2.7px 7.2px · 본문 5.4px 2.7px)는 0.5px.

### 붙이는 법 (각 모듈 작업자가 자기 마스터에)

   ```java
   public static final String HISTORY_TARGET = "WAREHOUSE";
   private final ChangeHistoryService changeHistory;
   // create: save 한 뒤
   changeHistory.record(HISTORY_TARGET, saved.getId(), ChangeHistoryService.CREATED);
   // update: 바꾸기 전 boolean wasActive = x.isActive(); … 바꾼 뒤
   changeHistory.recordUpdate(HISTORY_TARGET, x.getId(), wasActive, x.isActive());   // 사용 여부가 바뀌면 사용중단 · 재사용
   // (사용 여부가 없는 마스터) changeHistory.record(HISTORY_TARGET, x.getId(), ChangeHistoryService.UPDATED);
   // delete: changeHistory.record(HISTORY_TARGET, id, ChangeHistoryService.DELETED);
   // 사용중단/재사용 단추가 따로 있으면 그 메서드에서 STOPPED · REUSED
   ```

## 전표 번호 재사용 — 고치는 설계 (이번엔 안 함)

지금: `common/DocumentNoGenerator.next(prefix, table, noColumn, dateColumn, date)` 가 **남은 행의 max + 1** — 마지막 번호를 지우면 그 번호가 다시 나온다. 원본은 다시 쓰지 않는다.

1. **번호표** `document_sequences(prefix varchar(20), seq_date date, last_no integer NOT NULL, PRIMARY KEY(prefix, seq_date))` — 본사 `db/migration` · 테넌트 `db/tenant` 둘 다(7.4). 회사별 스키마라 테넌트 격리는 저절로.
2. **올리기는 한 문장**: `INSERT INTO document_sequences(prefix, seq_date, last_no) VALUES (?, ?, 1) ON CONFLICT (prefix, seq_date) DO UPDATE SET last_no = document_sequences.last_no + 1 RETURNING last_no` — 행 잠금으로 동시 저장도 겹치지 않는다(지금 max+1 은 두 저장이 같은 번호를 집을 수 있다). 지운다고 내리지 않는다.
3. **처음 한 번 따라잡기**: 그 (prefix, date) 행이 없을 때는 `GREATEST(1, 지금 max + 1)` 로 넣는다 — 번호표를 만들기 전 전표와 겹치지 않게. 마이그레이션에서 기존 전표의 (접두어, 일자)별 max 를 미리 넣어 두면 2번 한 문장만 남는다(표마다 `INSERT … SELECT prefix, date, max(split_part(no,'-',3)::int) … GROUP BY`).
4. `DocumentNoGenerator.next` 의 시그니처는 그대로 두고 안만 바꾼다 → 쓰는 서비스 56곳은 손대지 않는다. 따로 max+1 하는 리포지토리 7곳(BondEntry · BillingContract · ContractBill · TaxVoucher · OtherWithholding · MedicalSupplyEntry · DailyPayLedger)만 `DocumentNoGenerator` 로 옮긴다(접두어를 하나씩 정해서).
5. 날짜를 고쳐 전표를 다른 날로 옮길 때 번호를 새로 받는지는 원본에서 먼저 잰다(재지 않으면 지금처럼 그대로 둔다).
6. 검증: 같은 날 -1 · -2 저장 → -2 삭제 → 새 전표가 -3 인지(원본 회계2 실측과 같은지), 테넌트 회사에서도 같은지.

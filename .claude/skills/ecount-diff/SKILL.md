# 이카운트 원본 대조 한 바퀴

원본(loginad.ecount.com) 화면 **하나**를 열어 우리 화면과 견주고, 어긋난 것만 고친다.

## 0. 절대 규칙

- 이카운트는 **조회 화면만** 연다. 저장·수정·삭제·추가·권한요청·즐겨찾기 저장 등
  **어떤 쓰기 동작도 하지 않는다.** 저장 창이 뜨면 저장하지 않고 닫는다.
- 조건 판의 체크박스·드롭다운은 **재기 위해** 열어 볼 수 있다. 열었으면 **원래대로 되돌린다.**
- 원본을 못 보면(권한 없음·자료 없음·쓰기 화면) **값을 지어내지 않는다.**
  그 사실을 주석과 보드에 적고 다음 화면으로 넘어간다.

## 1. 보드를 먼저 읽는다 — 같은 화면을 두 번 열지 않기 위해

Notion 대조 보드: `collection://264a3744-cca8-4fe3-b00a-1e077f90f9f5`
(제조 ERP 프로젝트 > 🗺️ 원본 화면 대조 보드)

```
notion-query-data-sources (mode: sql)
SELECT "원본 화면", "화면코드", "메뉴 경로", "상태", "우리 화면", "남은 것"
FROM "collection://264a3744-cca8-4fe3-b00a-1e077f90f9f5"
ORDER BY "상태"
```

- `권한 없음` · `쓰기 화면(안 엶)` · `대조 불가(개인정보)` 인 화면은 **다시 열지 않는다.**
- `대조함·일치` 는 다시 보지 않는다.
- `대조함·남은 것 있음` 의 [남은 것] 이 **이번에 만들 수 있게 됐는지** 먼저 본다
  (앞 바퀴에 값을 만들어 두어 축이 생긴 경우가 실제로 여러 번 있었다).
- 그다음 `안 봄` 또는 보드에 없는 화면을 고른다. 고를 때는 qa/fixtures 의
  `pending-conditions.json` · `pending-period.json` · `pending-columns.json` 도 같이 본다.

## 2. 원본을 잰다

1. `mcp__claude-in-chrome__tabs_context_mcp` → 탭 확보. 로그인은 저장된 값으로 버튼만 누른다
   (비밀번호를 직접 입력하지 않는다).
2. 좌측 메뉴나 상단 **메뉴검색** 칸으로 화면을 연다.
3. 조건 판을 연다 — 목록 화면은 우측 상단 **Search(F3)**, 현황·비교표는 열자마자 조건 판이다.
   화면 제목 왼쪽의 작은 표시를 누르면 **즐겨찾기 저장 창**이 뜬다 — 그건 조건 판이 아니다.
4. `get_page_text` 로 라벨을 **글자 그대로** 받아 적는다. 드롭다운 후보는 열고 `find` 로 읽는다.
5. 잰 것: **조건 이름과 차례 · 기본값(기간 빠른선택 이름·라디오·체크박스) · 격자 열 차례 ·
   버튼줄 · 빈 목록 문구**.

## 3. 우리 화면과 견준다

`qa/fixtures/.ordermap.json` 에서 원본 이름 → 우리 파일을 찾는다.

자주 나온 어긋남(먼저 보라):

| 무엇 | 어떻게 드러나나 |
|------|-----------------|
| 기본 기간·기본 구분이 다름 | 첫 화면에 **다른 숫자**가 보인다. `ecount-period-default.json` · `ecount-mode-default.json` |
| 조건이 없음 | 표에는 열로 찍히는데 **그 값으로 거를 수가 없다** |
| 조건 차례가 다름 | ui-check 의 조건 차례 검사가 잡는다 |
| 열은 있는데 서버가 값을 안 보냄 | **늘 빈칸**이라 아무도 못 알아챈다. 응답 record 에 그 필드가 있는지 본다 |
| 우리가 원본에 없는 것을 만듦 | 버튼·조건이 하나 더 있다. 뺀다 |
| 대조표끼리 어긋남 | 두 fixture 가 같은 값을 다르게 적는다 — 원본이 심판이다 |

**못 만드는 것은 지어내지 않는다.** 우리 도메인에 값이 없으면 그 이유를 화면 주석에 적고
`qa/fixtures/pending-conditions.json` 에 올리거나, 이미 예외로 적혀 있으면 그대로 둔다.
반대로 **이제 만들 수 있게 된 예외는 예외에서 빼고 목록으로 옮긴다** — 이유를 고쳐 쓸 것이
아니라 만들 일이다.

## 4. 검증 — 전부 통과해야 한다

```
cd frontend && npm run typecheck && npm run test:unit
node qa/ui-check.mjs
node qa/dto-check.mjs
node qa/qa.mjs
cd backend && ./mvnw -o -q compile      # 백엔드를 건드렸을 때만
```

qa.mjs 는 **떠 있는 앱**에 대고 잰다. 백엔드를 고쳤으면 그 판은 아직 옛 클래스로 도는 것이니,
"다음 기동 때 확인된다" 고 커밋 메시지와 보드에 적는다.

## 5. 커밋·푸시

`origin feat/ecount-status-screens-and-sales-plan` 에 푸시한다.
커밋 제목은 **무엇이 문제였는지**가 보이게 쓴다. 스키마를 건드렸으면 본사(`db/migration`)와
테넌트(`db/tenant`) 마이그레이션을 **둘 다** 같은 커밋에 넣는다.

## 6. 보드와 기록을 갱신한다 — 이게 다음 바퀴를 아끼는 일이다

1. **대조 보드**(`collection://264a3744-cca8-4fe3-b00a-1e077f90f9f5`)에 그 화면 행을
   만들거나 고친다: 상태 · 우리 화면 · 잰 날짜 · 어긋난 것 · **남은 것(과 그 이유)** · 커밋.
   `남은 것` 을 성의 있게 적어야 다음 바퀴가 헛돌지 않는다.
2. **작업 기록**(`collection://f5a413c2-6b78-4d3b-a73b-59b6f573ff73`)에 한 행 남긴다.

## 7. 대화에는 3~5줄만

무엇이 문제였고 무엇을 고쳤는지만 적는다. 잰 값을 통째로 붙여넣지 않는다 — 그건 보드에 있다.

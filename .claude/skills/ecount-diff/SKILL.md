# 이카운트 모듈 · 메뉴 묶음 하나를 똑같이 만들기

원본: **https://loginaa.ecount.com/ec56/view/erp** (테스트 회사 — 자료를 넣고 고치고 지워도 된다)

인자: `/ecount-diff <모듈> [메뉴 묶음] [이카운트 주소]`

```
/ecount-diff 회계1                      # 모듈 전체 — 첫 묶음부터 차례로 (묶음 하나 끝날 때마다 알린다)
/ecount-diff 회계1 고정자산              # 회계 I > 고정자산 아래만
/ecount-diff 재고1 영업관리 > 판매        # 더 잘게: 재고 I > 영업관리 > 판매 아래만
/ecount-diff 세무 원천징수 https://loginaa.ecount.com/ec56/view/erp?w_flag=1&ec_req_sid=…   # 이 주소로 들어간다
```

- 모듈이 없으면 사용자에게 묻는다.
- **메뉴 묶음**은 사이트맵에서 모듈 아래 이름 그대로다(`>` 로 더 깊이). 일은 **묶음 하나씩** 한다 — 그 묶음 화면이 다 끝나기 전에는 다른 묶음 화면을 집지 않는다.
  묶음을 안 주면 그 모듈 사이트맵의 **첫 묶음**부터 하고, 하나 끝날 때마다 다음 묶음으로 넘어가기 전에 사용자에게 한 줄로 알린다.
- **이카운트 주소**(`ec_req_sid=` 가 든 것)를 주면 그 주소로 들어간다. 하위 에이전트에게도 그대로 넘긴다. 안 주면 위 원본 주소로 들어가고, 로그인 화면이면 멈추고 새 주소를 받는다.
- 같은 모듈을 여러 진행자가 돌릴 때는 **묶음을 나눠** 맡긴다(같은 묶음을 둘이 맡지 않는다). 보드에 '작업 중' 선택지가 없어서, 겹침은 이것으로만 막는다.

| 인자 | 이카운트 사이트맵 모듈 |
|------|------------------------|
| `mypage` | MyPage |
| `self` | Self-Customizing |
| `재고1` · `재고2` | 재고 I · 재고 II |
| `회계1` · `회계2` | 회계 I · 회계 II |
| `관리` · `세무` · `그룹웨어` · `데이터센터` | 같은 이름 |

**내 모듈(묶음) 밖의 화면은 고치지 않는다.** 다른 프로세스가 그 모듈 · 묶음을 돌고 있다.
내 모듈의 자료가 다른 모듈 화면에 반영되는지(예: 판매 → 회계전표)는 **보기만** 하고, 어긋나면 보드에 적는다.

한 바퀴 = **화면 하나**: 고르기 → 원본 CRUD 로 재기 → 우리 화면 견주기 → 기능·로직·디자인 고치기 → 검증 → 커밋 → 기록.

**누가 무엇을 하나**(7장): 이 스킬을 부른 세션은 **진행자**다. 1장(화면 고르기)만 직접 하고, 2~6장은 화면마다
**새 하위 에이전트**에게 맡긴다. 앞 바퀴의 브라우저 출력·빌드 로그가 다음 바퀴 문맥에 쌓이지 않게 하려는 것이다.

## 0. 이카운트에서 해도 되는 것 · 안 되는 것

**해도 된다**(loginaa 는 테스트 회사 — 2026-10-03 사용자 확인):

- 전표·마스터 **등록 · 수정 · 삭제**, 입력 화면 열기, 조건 바꿔 조회, 상태 바꾸기(확인·마감·회계반영 …).
- 저장한 자료가 **어디로 흘러가는지** 다른 화면(현황·장부·전표·재고)을 열어 확인하는 것.
- `javascript_tool` 로 읽기(`getComputedStyle` · `textContent`). 입력은 사람처럼 화면에서 한다.

**안 된다** — 회사 밖이나 다른 프로세스에 닿는 것:

- **바깥으로 나가는 것**: 전자세금계산서 국세청 전송, 이메일 · SMS · 팩스 · 카카오 발송, 결제 · 충전 · 유료 서비스 신청, 은행 · 카드사 연동 실행.
- **로그인을 흔드는 것**: 사용자 · 권한 · 비밀번호 · 보안정책 · 회사정보 변경. 다른 프로세스가 같은 계정으로 돌고 있다.
- **모든 화면을 바꾸는 설정**(Self-Customizing 의 환경설정 · 양식 · 기본값): `self` 프로세스만 바꾼다. 바꿨으면 재고 나서 **바로 원래대로 되돌리고** 보드에 적는다.
  다른 모듈 프로세스는 설정이 이상하게 보이면 건드리지 말고 1분 뒤 다시 본다.
- 운영 회사 `loginad.ecount.com` 은 열지 않는다.

**자료에는 내 표시를 단다.** 여러 프로세스가 같은 회사에 자료를 넣으므로 현황 숫자가 섞인다.

- 새로 만드는 품목 · 거래처 · 창고 · 계정 등 마스터 이름은 `QA<모듈>-` 로 시작한다(`QA재고1-볼트`).
- 전표의 적요 · 비고에 `QA<모듈>` 을 적는다.
- 숫자를 견줄 때는 **내 마스터로 거른 조회**로 본다. 회사 전체 합계로 보면 남의 자료가 섞인다.
- 바퀴 끝에 **내가 만든 자료는 지운다**(삭제 동작 확인을 겸한다). 다음 화면에 꼭 필요한 마스터만 남기고, 남긴 것은 보드에 적는다.
- 남의 표시(`QA다른모듈-`)가 붙은 자료는 고치지도 지우지도 않는다.

## 1. 화면을 고른다

Notion 대조 보드: `collection://264a3744-cca8-4fe3-b00a-1e077f90f9f5`

### 1.0 약속 — 모든 모듈이 같은 차례 · 같은 끝

1. **묶음 차례 = 이카운트 사이트맵의 위에서 아래.** 이카운트는 모듈마다 `기초등록 → 입력 → 조회 · 처리 → 출력물` 차례로 놓여 있다.
   그래서 마스터를 먼저 맞추고, 그 마스터로 전표를 넣고, 마지막에 출력물 · 장부 · 재무제표로 **앞에서 넣은 자료가 다 맞게 모이는지** 확인하며 끝난다.
2. **묶음 안의 화면 차례도 사이트맵 그대로.** 건너뛰지 않는다. 빠뜨린 화면은 묶음 끝에 남기지 말고 그 자리에서 한다.
3. **모든 화면을 같은 방법으로**: 2 ~ 6장(원본 · 우리 양쪽 직접 CRUD → 흐름 숫자 → 디자인 → 검증 → 커밋 → 기록), 끝 판정은 7장(양쪽 CRUD + 흐름 + 디자인 같음).
   화면 크기 · 남은 것 크기와 상관없이 같다.
4. **여러 모듈에 같은 화면이 있으면**(거래처등록 · 부서등록 · 프로젝트등록 · 사원(담당)등록 …) 사이트맵에서 **먼저 나오는 모듈**이 맡는다.
   뒤 모듈은 그 화면을 건너뛰되, 그 모듈 메뉴에서 열었을 때 다른 것(기본값 · 열)이 있는지만 본다.
5. **한 묶음이 끝나면 알린다**: `회계 I > 고정자산 끝 — 9화면 일치 7 · 남은 것 2(이유)`. 그다음 묶음으로.

   ```
   WHERE "메뉴 경로" LIKE '<사이트맵 모듈 이름> > <묶음>%'   -- 예: '회계 I > 고정자산%'
      OR "메뉴 경로" LIKE '<묶음>%'                          -- 예전 행은 모듈 이름 없이 '영업관리 > …' 로 적혀 있다
   ```
   예전 행(모듈 이름이 없는 경로)을 찾으면 그 행의 `메뉴 경로` 를 `<모듈> > …` 꼴로 고쳐 둔다. 안 고치면 다음 진행자에게 안 보인다.
   사이트맵에는 있는데 보드에 없는 화면은 `안 봄` 행을 새로 만든다.
3. 사용자에게 묶음 목록을 한 번 보여 준다: `회계 I > 고정자산 — 8화면: 남은 것 7 · 고침 0 · 일치 0`.

**바퀴마다** — 목록 차례대로 다음 화면을 고른다:

- 건너뛰는 것: 7장 기준으로 `대조함·일치` 인 것(양쪽 CRUD + 흐름 + 디자인 기록이 있는 것) · `권한 없음` · `대조 불가(개인정보)`.
  그 밖(`남은 것 있음` · `고침` · 기록 없는 `일치` · `안 봄`)은 모두 차례가 오면 한다.
- 입력 화면과 그 조회 · 현황 화면은 한 바퀴로 묶어도 된다(같은 자료를 본다). 같은 틀의 출력물 여럿도 묶어도 된다.
- 묶음의 화면이 모두 건너뛰는 것이 되면 **묶음 끝** — 보드 숫자와 함께 알리고, 묶음을 받았으면 멈추고 / 모듈만 받았으면 다음 묶음으로.
- 원본 이름 → 우리 파일: `qa/fixtures/.ordermap.json`. 우리에게 없는 화면이면 **새로 만든다**(라우트 · 메뉴 · 권한까지 — 4장).

## 2. 원본을 잰다 — 직접 써 보면서

1. `tabs_context_mcp` → **새 탭을 만들어 내 탭으로만 쓴다**(다른 프로세스의 탭은 건드리지 않는다). 바퀴가 끝나면 그 탭을 닫는다.
   **탭은 하나만 쓴다** — 이카운트와 우리 앱(5180)을 그 한 탭에서 `navigate` 로 오간다(이카운트로 돌아갈 땐 받은 주소로).
   작업자마다 탭을 둘씩 열면 8명이 16탭이 되어 메모리 8GB 기계의 스왑이 바닥난다(2026-10-13 여유 445MB).
   단 **그룹의 마지막 탭이면 닫지 않고** `about:blank` 로 두고 끝낸다 — 마지막 탭을 닫으면 탭 그룹이 통째로 사라지고,
   다른 작업자가 새로 만든 그룹은 로그인이 안 된 창에서 열려 로그인 화면이 뜬다(2026-10-13 재고2 가 이렇게 멈췄다).
   로그인 화면이 떴는데 같은 그룹의 다른 이카운트 탭 제목이 로그인 화면이 아니면, 세션은 살아 있다 — 받은 주소로 한 번 더 열어 본다.
   이 Chrome 은 **모든 작업자가 같이 쓰는 창 하나**다. 화면 좌표로 누르기 · 스크린샷(`computer`)은 탭을 앞으로 끌어와야 해서
   작업자끼리 탭을 빼앗는다. 그래서 **읽기**는 `javascript_tool` · `find` 로 하고, 스크린샷은 아낀다.
   **입력 · 누르기는 아끼지 않는다** — 칸을 누르고 글자를 치고 코드도움에서 고르고 [저장] 을 누르는 것은 사람처럼 화면에서 한다
   (`find` 의 ref 로 `computer` 클릭 · 입력, `form_input`). `javascript_tool` 로 값을 넣거나 API 를 직접 불러 저장하지 않는다 —
   그러면 화면의 자동 계산 · 검증 · 저장 후 안내를 못 보고, 그걸 재러 온 것이다.
   **로그인 화면이 보이면 아무것도 누르지 않고 바로 멈춘다** — 다시 시도하지 않는다. 결과에 `LOGIN_EXPIRED` 를 적고 끝낸다(7장).
2. **사이트맵 → 내 모듈 → `find`** 로 연다. 메뉴검색 칸은 화면 이름을 못 찾을 때가 많다. 좌표 대신 `find` 의 ref 로 누른다.
3. 아래를 **글자 그대로** 적는다. **`get_page_text` 는 쓰지 않는다** — 이카운트는 상단·왼쪽 메뉴 글자까지 통째로 딸려 와
   한 번에 수천 토큰이 든다. 아래 **추출 스니펫**을 `javascript_tool` 로 돌려 필요한 것만 JSON 으로 받는다.
   스크린샷은 디자인을 나란히 견줄 때 **화면당 한두 장**만 찍는다(값은 스니펫의 `style` 로 본다).

   ```js
   (() => {
     const vis = el => !!el && el.offsetParent !== null;
     const txt = el => (el?.textContent || '').replace(/\s+/g, ' ').trim();
     const pick = el => { if (!el) return null; const s = getComputedStyle(el); return { font: s.fontSize+' '+s.fontWeight,
       color: s.color, bg: s.backgroundColor, h: Math.round(el.getBoundingClientRect().height*10)/10, pad: s.padding,
       border: s.borderBottom, align: s.textAlign } };
     // 본문 격자 = 보이는 표 중 (줄 수 × 폭) 이 가장 큰 것
     const grid = [...document.querySelectorAll('table')].filter(t => vis(t) && t.rows.length > 1)
       .sort((a, b) => b.rows.length*b.offsetWidth - a.rows.length*a.offsetWidth)[0];
     const cells = r => [...r.cells].map(txt);
     const uniq = a => [...new Set(a.filter(t => t && t.length < 25))];
     // 머리·메뉴 영역은 뺀다(원본 DOM 에 맞게 셀렉터를 좁혔으면 이 줄을 고쳐 스킬에 다시 적는다)
     const outside = el => !el.closest('header, nav, .gnb, .lnb, [class*="menu"]') && !grid?.contains(el);
     const out = {
       title: txt(document.querySelector('h1, h2, .title, [class*="title"]')),
       labels: uniq([...document.querySelectorAll('label, th, .label')].filter(el => vis(el) && outside(el)).map(txt)),
       head: grid ? [...grid.querySelectorAll('thead tr')].map(cells) : [],
       rows: grid ? [...(grid.tBodies[0]?.rows || [])].slice(0, 5).map(cells) : [],   // 5줄만
       foot: grid?.tFoot ? [...grid.tFoot.rows].map(cells) : [],
       buttons: uniq([...document.querySelectorAll('button, a.btn, [role="button"]')].filter(el => vis(el) && outside(el)).map(txt)),
       style: grid && { th: pick(grid.querySelector('th')), td: pick(grid.querySelector('tbody td')),
         stripe: [...(grid.tBodies[0]?.rows || [])].slice(0, 4).map(r => getComputedStyle(r).backgroundColor),
         foot: pick(grid.tFoot?.rows[0]?.cells[0]) },
     };
     return JSON.stringify(out).slice(0, 6000);
   })()
   ```
   우리 화면(5180)에서도 **같은 스니펫**을 돌려 두 JSON 을 견준다. 입력 창 · 확인 창 문구처럼 스니펫이 못 잡는 것만
   `find` 로 그 부분을 집어 읽는다. 스니펫은 **화면을 읽는 도구일 뿐이다** — 조회 화면을 읽은 것으로 바퀴가 끝나지 않는다.
   아래 등록 · 수정 · 삭제 · 검증을 실제로 해 보고, 4번의 흐름을 따라간 뒤에야 원본을 잰 것이다.

   적을 것:

| 무엇 | 볼 것 |
|------|-------|
| 조회 | 조건 이름 · 차례 · 기본값(기간 빠른선택 · 라디오 · 체크박스) · 격자 열 차례 · 합계 · 소계줄 · 빈 목록 문구 · 버튼줄 |
| 등록 | 입력칸 · 필수 표시 · 기본값 · 코드도움(무엇을 띄우고 고르면 무엇이 채워지나) · 자동 계산(공급가 → 부가세 · 합계, 단가 불러오기) · 저장 후 안내 문구 · 번호 매기는 규칙 |
| 수정 | 어떤 칸이 막히나 · 상태에 따라 수정이 막히나(마감 · 회계반영 후) · 수정하면 연결된 자료가 같이 바뀌나 |
| 삭제 | 확인 창 문구 · 삭제가 막히는 조건(연결 전표 · 마감) · 지우면 연결된 자료가 같이 사라지나 · 되돌리기 |
| 검증 | 일부러 틀리게 넣어 본다(빈 필수칸 · 음수 · 재고 부족 · 날짜 마감) → 막는 문구를 글자 그대로 |

4. **자료가 어디로 가나 따라간다** — 이게 이번 루프의 핵심이다.
   저장한 다음 그 자료가 보일 만한 화면을 열어 **숫자로** 확인한다:
   - 재고: 재고현황 · 재고수불부 · 창고별 재고 — 늘었나 줄었나, 얼마나
   - 돈: 회계전표 생성 여부 · 계정 · 차대 금액 · 거래처별 채권/채무 · 미수 · 미지급
   - 진행: 주문 → 출하 → 판매 처럼 다음 단계 화면에 '진행/완료' 로 넘어가나, 잔량이 줄었나
   - 그리고 **수정 · 삭제 뒤에 그 화면들이 다시 어떻게 되는지**도 본다(되돌려지나, 남나).
   흐름을 표로 남긴다: `판매 1건(QA재고1-볼트 10개 × 1,000) → 재고 -10 · 외상매출금 차 11,000 / 매출 10,000 · 부가세 1,000 · 거래처 채권 +11,000`.
5. **디자인을 잰다** — 자료가 든 판에서 `getComputedStyle` 로 읽는다(아래 3.3).

원본에서 못 보는 것(권한 없음 · 바깥 연동 필요)은 **지어내지 않는다.** 그 사실을 보드에 적고 넘어간다.

## 3. 우리 화면을 같게 만든다

우리 앱: 백엔드 8081 · 프론트 5180. 우리 화면에서도 **원본에서 한 것과 같은 CRUD 를 똑같이 해 본다**(같은 `QA<모듈>-` 자료로).

### 3.1 기능

조건 · 기본값 · 열 · 버튼 · 입력칸 · 검증 문구 · 저장 후 안내를 원본 글자 그대로 맞춘다.
우리에게만 있는 버튼 · 조건은 뺀다. 열은 있는데 서버가 값을 안 보내 늘 빈칸인 곳이 자주 있다 — 응답 record 를 본다.

### 3.2 로직 — 2장 4번의 흐름표와 숫자가 같아야 한다

우리 화면에서 같은 자료를 저장 · 수정 · 삭제하고, 같은 '따라갈 화면'들을 열어 **흐름표의 숫자가 같은지** 확인한다.
다르면 서비스 로직을 고친다(재고 반영 · 전표 생성 · 상태 전이 · 삭제 시 되돌리기 · 막는 조건).

- 모듈 경계는 CLAUDE.md 4장을 따른다 — 다른 모듈의 상태를 바꾸는 것은 그 모듈의 `service` 로.
- 스키마를 바꾸면 `db/migration` 과 `db/tenant` **둘 다**. 번호는 `ls` 로 정하지 않고 **`bash qa/next-migration.sh`** 로 잡는다
  (본사 · 테넌트 번호 한 쌍을 원자적으로 예약한다. `ls` + 1 은 두 작업자가 같은 번호를 집는다).
  잡았으면 미루지 말고 파일 쓰기 → 커밋 → 재기동까지 한 번에 한다. `outOfOrder` 가 꺼져 있어서, 내 번호보다 큰 번호가 먼저 적용되면
  내 마이그레이션 때문에 **백엔드 기동이 통째로 실패한다**(모든 작업자가 멈춘다). 기동이 그렇게 실패하면 바로 사용자에게 알린다.
- enum 값을 늘리면 CHECK 제약 마이그레이션도 — `node qa/schema-check.mjs`.
- 자바 메서드를 기존 메서드 위에 넣을 때 그 위의 `@Transactional` 이 누구 것인지 먼저 본다.
  사이에 끼우면 원래 주인이 트랜잭션을 잃어 500(no session) 이 나거나, 애노테이션이 겹쳐 컴파일이 깨지고 Lombok 오류가 수백 줄 딸려 나온다.
  오류가 쏟아지면 `./mvnw -o compile | grep -E '^\[ERROR\].*\.java' | head -3` 로 **첫 줄**부터 읽는다.

### 3.3 디자인 — 나란히 놓아 구별이 안 되게

규칙은 CLAUDE.md 10.1 · 10.2 를 따른다(토큰 단일 출처 `styles/tokens.css`, 부품 `styles/index.css` · `shell.css`, 화면 코드에 색 · px 금지).

- **원본에서 값을 읽어** 맞춘다. 눈대중으로 하지 않는다. 격자 머리 · 본문 줄 · 합계줄 · 숫자 칸(쉼표 · 0 표시 · 음수) · 조건 판 · 입력 폼 · 버튼줄 · 빈 목록.
  2장 추출 스니펫의 `style` 이 격자 값을 준다. 다른 요소는 그 안의 `pick` 만 떼어 `find` 로 집은 요소에 돌린다.
- 줄무늬는 **줄 차례대로** 읽는다(스니펫의 `stripe`). 색을 `Set` 으로 모으면 합계줄 회색이 줄무늬처럼 보인다.
- 값은 반올림하지 않는다(원본 여백이 정수 × 0.9 로 그려진다). 새 값은 `tokens.css` 에 이름을 붙여 더한다.
- **공용 부품(tokens · index.css · shell.css · EcListShell · Ec*)을 고치면 모든 모듈 화면이 바뀐다.**
  원본의 모든 화면이 같은 모양일 때만 고치고, 고치기 전후로 `node qa/style-snapshot.mjs` 로 다른 화면이 안 바뀌었는지 보고, 보드에 적는다.
  내 화면만 다르면 그 화면에서만 고친다.
- 휴대폰 폭도 본다: `ROUTES=/내/화면 node qa/mobile-check.mjs`.
- 우리 화면에서도 같은 `pick` 으로 읽어 **숫자로** 견주고, 같은 창 크기로 원본과 나란히 찍어 본다.

## 4. 검증

```bash
bash qa/precommit.sh                       # typecheck · test:unit · ui-check · dto-check · arch-check · style-check
cd backend && ./mvnw -o -q compile         # 백엔드를 건드렸을 때
node qa/schema-check.mjs                   # 스키마 · enum 을 건드렸을 때
node qa/screen-check.mjs <접두사>           # 내 화면들
node qa/shot.mjs qa/flows/<내 흐름>.json     # 입력 화면을 고쳤으면 흐름을 하나 더해 두고 돌린다
```

- 입력 화면을 고쳤으면 `qa/flows/` 에 **입력 → 저장 → 안내 → 따라갈 화면 숫자 → 삭제** 흐름을 더한다.
- **무거운 명령은 한 번에 하나만 돈다**(이 컴퓨터는 메모리 8GB — 타입체크 · `mvn compile` · 헤드리스 Chrome 이 각각 1GB 안팎이라 여럿이 겹치면 스왑으로 다 같이 멈춘다).
  `precommit.sh` · `./mvnw` · `screen-check` · `mobile-check` · `style-snapshot` · `shot.mjs` 는 이 잠금 안에서만 돌린다:
  ```bash
  H=/tmp/erp-heavy.lock
  [ -d $H ] && [ -n "$(find $H -maxdepth 0 -mmin +15)" ] && rm -rf $H     # 15분 넘은 잠금은 죽은 작업자 것
  until mkdir $H 2>/dev/null; do sleep 20; done; echo "<모듈> $(date +%T)" > $H/owner
  bash qa/precommit.sh; rc=$?; rm -rf $H; exit $rc                     # 끝나면 꼭 푼다(실패해도)
  ```
  기다리는 동안 다른 일(원본 재기 · 코드 읽기)을 한다. 백엔드 재기동 잠금과는 별개다.
- 백엔드 재기동은 모든 작업자가 쓰는 서버(8081)를 내렸다 올리는 일이다. 재기동하는 1~2분 동안 **남의 QA 가 전부 실패**하므로:
  - 재기동은 바퀴마다 **한 번만** 한다. 백엔드를 여러 번 고쳐야 하면 컴파일(`./mvnw -o -q compile`)로 확인해 가며 모았다가 마지막에 한 번.
  - 잠금 안에서만 한다. 잠금 폴더에 내 정보를 남겨, 잠근 쪽이 죽어도 남이 영원히 기다리지 않게 한다:
    ```bash
    L=/tmp/erp-backend-restart.lock
    # 15분 넘은 잠금은 죽은 작업자가 남긴 것이다 — 치운다
    [ -d $L ] && [ -n "$(find $L -maxdepth 0 -mmin +15)" ] && rm -rf $L
    mkdir $L && { echo "<모듈> $(date +%T)" > $L/owner; (cd backend && ./mvnw -o -q compile) && { …서버 내리고 올리기…; 뜰 때까지 기다림; }; rm -rf $L; } || cat $L/owner
    ```
    **컴파일이 성공한 다음에만 서버를 내린다.** 컴파일 실패면 서버는 그대로 두고 잠금을 풀고, 실패한 파일이 남의 것이면(반쯤 커밋된 변경) 2분 뒤 다시 한다.
    2026-10-13 재고1 이 컴파일을 안 보고 서버부터 내렸다가, 남의 반쯤 들어온 DTO 때문에 못 올려 3~4분 동안 모두의 백엔드가 꺼졌다.
    `mkdir` 이 실패하면 재기동하지 않는다(`;` 로 잇지 않는다 — 남의 잠금을 지나쳐 재기동하고 그 잠금을 지운 적이 있다).
    누가 잡고 있는지 `owner` 로 보고, 2분 뒤 한 번 더 해 본다. 그래도 잠겨 있으면 다른 일(디자인 · 프론트)을 먼저 한다.
  - 내가 재기동하지 않았는데 API 가 갑자기 연결 거부 · 502 를 내면 남이 재기동 중이다. 내 탓으로 고치려 들지 말고 2분 뒤 다시 본다.
- precommit 은 **트리 전체**를 본다. 남이 고치다 만 파일 때문에 실패할 수 있다:
  - 실패 줄의 파일이 **내가 고친 파일인지** 먼저 본다(`git status` 와 대조). 내 파일이 아니면 내 커밋은 막지 않는다 —
    **다시 돌리며 기다리지 않는다.** 커밋 메시지 끝에 `precommit: <검사> 실패는 <파일>(남의 작업 중) 탓` 이라고 적고 넘어간다.
  - style-check 기준은 **내 파일만** 고친다: `node qa/style-check.mjs --update <내가 고친 .tsx …>`.
    인자 없는 `--update` 는 남의 작업 중인 개수까지 기준에 적어 넣어, 그 기준을 커밋하면 남의 변경이 섞인다.
- QA 브라우저(`shot` · `screen-check` · `mobile-check` · `style-snapshot`)는 빈 포트를 알아서 잡으므로 동시에 돌려도 된다.
  `CDP_PORT` 를 직접 주지 않는다(같은 포트를 주면 남의 Chrome 에 붙는다).
- `screen-check` 는 **내 접두사만** 돌린다(전체는 8분이고, 여럿이 동시에 돌리면 백엔드 · 프론트가 같이 느려진다).

## 5. 커밋 · 푸시 — 같은 작업 트리를 여럿이 쓴다

- **내가 고친 파일만** `git add <경로>` 로 올린다. `git add -A` · `git add .` 는 쓰지 않는다.
- 남의 변경을 `checkout -- ` · `restore` · `reset` · `stash` 로 되돌리지 않는다. 같은 파일을 남이 고치고 있으면 내 hunk 만 `git add -p` 로.
- 공용 파일(`router.tsx` · `EcountLayout.tsx` · `menuPermissions.ts` · `tokens.css` · `index.css` · `shell.css` · 마이그레이션)은 고치면 **바로** 커밋한다 — 오래 들고 있을수록 겹친다.
- `.git/index.lock` 이 있다는 오류가 나면 남이 지금 git 을 쓰는 중이다. **lock 파일을 지우지 않고** 몇 초 뒤 다시 한다.
  `pgrep -x git` 이 비어 있는데도 1분 넘게 남아 있을 때만 지운다.
- 커밋 제목은 `fix(<화면>): <무엇이 원본과 달랐나>` 처럼 문제가 보이게. 지금 체크아웃된 브랜치에 커밋하고 그 브랜치의 origin 으로 푸시한다. 푸시가 거절되면 `git pull --rebase` 후 다시.

## 7. 진행자 — 화면마다 새 하위 에이전트, 쉬지 않고 다음

이 스킬을 부른 세션(진행자)은 **브라우저도 코드도 직접 만지지 않는다.** 바퀴마다 이렇게 한다:

1. 1장대로 묶음 목록에서 다음 화면을 고른다.
2. `Agent(subagent_type: "general-purpose")` 를 **새로** 띄운다(SendMessage 로 앞 에이전트를 이어 쓰지 않는다 — 문맥이 쌓인다):
   ```
   .claude/skills/ecount-diff/SKILL.md 의 0 · 2 ~ 6장을 읽고 그대로 한 바퀴 돌아라.
   모듈: <모듈>  묶음: <메뉴 묶음>  화면: <원본 화면> (<화면코드>, <메뉴 경로>)  보드 행: <행 URL>  우리 화면: <경로 또는 '없음'>
   이카운트 주소: <받은 주소 — 이 주소로 들어간다>
   보드에 적힌 남은 것: <남은 것>
   끝나면 아래 형식으로만 답한다(다른 말 없이):
   STATUS: DONE | LOGIN_EXPIRED | RATE_LIMITED | BLOCKED
   SCREEN: <원본 화면>
   CRUD: 등록 원본○/우리○ · 수정 ○/○ · 삭제 ○/○ · 검증 ○/○   (안 했으면 × 와 이유: 조회 전용 · 권한 없음 · 바깥 연동 …)
   FLOW: <흐름표 한 줄 — 원본 숫자 / 우리 숫자, 같음 · 다름>
   BOARD: 대조함·일치 | 대조함·남은 것 있음
   COMMITS: <해시 …>
   SUMMARY: <무엇이 달랐고 무엇을 고쳤나, 3줄 이내>
   ```
   `BOARD: 대조함·일치` 는 **CRUD 가 원본 · 우리 양쪽에서 모두 ○(또는 그 화면에 없는 동작이라 ×)이고, FLOW 가 '같음'일 때만** 쓴다.
   조회만 해 봤거나 흐름을 못 따라갔으면 `대조함·남은 것 있음` 이다.
3. 결과가 오면 진행자가 **보고를 확인한다**: `CRUD` 에 이유 없는 × 가 있거나, 등록이 있는 화면인데 `FLOW` 가 비었는데 `BOARD` 가 `일치` 면
   보드를 `대조함·남은 것 있음` 으로 고쳐 적는다(그 화면은 다음에 다시 집힌다).
   그다음 `SUMMARY` 만 대화에 옮기고 **바로** 다음 화면으로 1번부터 다시 한다. 기다리지 않는다.
   에이전트가 돌아가는 동안 진행자는 끝난다. 에이전트가 끝나면 알림이 와서 다시 불리므로, 중간에 상태를 묻는 짧은 깨우기를 잡지 않는다.
   `/loop` 안이라면 혹시 알림이 안 올 때를 대비한 `ScheduleWakeup(delaySeconds: 1800)` 하나만 둔다.

**멈추는 때** — 아래면 다음 에이전트를 띄우지 않는다. `/loop` 안이면 `ScheduleWakeup(stop: true)` 로 루프를 끝내고, 사용자에게 한 줄로 알린다:

- `LOGIN_EXPIRED`: 이카운트 로그인 화면이 떴다. **재시도하지 않는다** — 사용자가 다시 로그인해 새 주소를 줄 때까지 아무것도 하지 않는다.
  하던 화면은 보드에 그대로 남아 있으므로, 새 주소로 다시 부르면 묶음 목록 차례대로 그 화면부터 다시 한다.
- `RATE_LIMITED`: 사용량 한도(429). 재시도하지 않는다.
- `BLOCKED`: 브라우저 도구가 2~3번 연속 실패했거나, 사용자가 정해야 할 것이 있다 → 무엇인지 알린다.
- 실수로 **안 되는 것**(0장)을 눌렀다 → 숨기지 않고 바로 알린다.
- 묶음이 끝났다(1장) → 묶음을 받았으면 알리고 끝낸다. 모듈만 받았으면 한 줄로 알리고 다음 묶음으로 간다.
- 모듈의 모든 묶음이 끝났다 → 알리고 끝낸다.

하위 에이전트도 같다. 2장 1번에서 로그인 화면을 보거나 429 를 받으면 그 자리에서 멈추고 위 형식으로 보고한다.
